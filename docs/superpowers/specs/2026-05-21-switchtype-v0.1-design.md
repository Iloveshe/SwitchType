# SwitchType v0.1 Design

Date: 2026-05-21

## Goal

SwitchType is a local-first macOS voice typing tool for bilingual developer workflows. The first release proves the workflow with a CLI benchmark, then delivers a macOS menu bar app that records speech while a global hotkey is held, transcribes locally, applies a personal technical-term correction layer, and pastes the result into the active text field.

The project will be suitable for publishing on GitHub with a clear README, setup steps, benchmark results, demo assets or demo recording instructions, and a roadmap.

## Target User

The primary user is a developer who frequently dictates Chinese-English mixed technical text on macOS. Common vocabulary includes terms such as Codex, MCP, SeaTalk, prelive, Go, PR, issue, CI, branch names, project names, and internal product names.

## Success Criteria

- The repository contains a reproducible CLI benchmark for at least two local ASR paths.
- The benchmark can evaluate real Chinese-English technical samples against reference transcripts.
- The benchmark reports latency, transcription accuracy, and technical-term accuracy.
- The macOS app can run as a menu bar app.
- Holding the configured global hotkey starts recording, and releasing it stops recording.
- Transcription runs locally without cloud ASR.
- Post-processing protects and corrects personal technical terms.
- The final text is copied to the clipboard and pasted into the active text field.
- README documentation explains setup, model requirements, benchmark usage, app usage, and limitations.

## Non-Goals for v0.1

- Do not build a full macOS input method.
- Do not build iOS or Android versions.
- Do not use cloud ASR.
- Do not train or fine-tune models.
- Do not build a complex settings UI.
- Do not attempt automatic per-user acoustic adaptation.

## Architecture

SwitchType has two product surfaces:

1. CLI benchmark
2. macOS menu bar app

The benchmark is built first because it validates whether local ASR plus personal post-processing is worth using before investing in the app workflow.

The app path stays simpler than the benchmark path. In v0.1, the app uses whisper.cpp as the main local transcription engine. SenseVoice or FunASR is benchmark-only until packaging, dependency, and runtime behavior are proven.

## CLI Benchmark

The benchmark compares local ASR engines on the user's real Chinese-English technical samples.

Inputs:

- A JSONL manifest of sample audio files and reference transcripts.
- A benchmark config describing enabled ASR engines and model paths.
- A hotword config for technical-term correction.

Outputs:

- Raw transcripts per engine.
- Post-processed transcripts per engine.
- Metrics per sample and per engine.
- A Markdown summary table for README inclusion.

Initial engines:

- `whisper.cpp`: primary candidate for the app path.
- `SenseVoice/FunASR`: benchmark candidate for Chinese-English mixed accuracy. The runner is part of the benchmark design, and execution can be skipped with a clear setup warning if local dependencies are unavailable.

Metrics:

- End-to-end latency in milliseconds.
- Character error rate for Chinese-heavy text.
- Word error rate for English-heavy spans.
- Technical-term accuracy for configured hotwords.
- Post-processing delta so the correction layer can be evaluated separately from ASR.

## macOS App

The app is a menu bar utility.

Core behavior:

1. User holds the global hotkey, default `Option + Space`.
2. App records microphone audio to a temporary local file.
3. User releases the hotkey.
4. App sends the audio file to the local transcription service.
5. App applies post-processing.
6. App writes the final text to the clipboard.
7. App triggers paste into the active application.
8. App removes temporary audio files.

The first UI is minimal:

- Menu bar status item.
- Start/stop status.
- Link or menu item for permission guidance.
- Quit action.

The app avoids a full settings window in v0.1. User-editable configs live in documented files first.

## Components

### AudioRecorder

Owns microphone capture and local temporary 16 kHz mono PCM WAV audio files. It exposes a small API:

- `startRecording()`
- `stopRecording() -> URL`
- `cleanup(URL)`

### HotkeyController

Owns global hotkey registration and key-down/key-up events. It does not own recording or transcription logic. It emits semantic events:

- `recordingRequested`
- `recordingFinished`

### TranscriptionService

Owns execution of the local ASR engine. For v0.1 this can invoke a local `whisper.cpp` binary with configured model and language options. It returns raw text plus timing metadata.

### PostProcessor

Owns deterministic text cleanup:

- Trim whitespace.
- Normalize common punctuation spacing.
- Protect configured technical terms.
- Apply configured replacements.
- Preserve all-caps technical tokens such as PR, CI, MCP.

This component should exist in both benchmark and app layers, with shared test cases or mirrored behavior.

### PasteboardTyper

Owns clipboard write and paste trigger. v0.1 overwrites the clipboard and documents that limitation. Clipboard preservation can be added after the end-to-end workflow is reliable.

### AppState

Owns user-visible state:

- Idle
- Recording
- Transcribing
- Pasting
- Error

## Data Flow

```text
Hotkey down
  -> AudioRecorder.startRecording()
Hotkey up
  -> AudioRecorder.stopRecording()
  -> TranscriptionService.transcribe(audio)
  -> PostProcessor.process(rawText)
  -> PasteboardTyper.paste(finalText)
  -> AudioRecorder.cleanup(audio)
```

The benchmark data flow is similar but file-oriented:

```text
manifest sample
  -> ASR engine transcript
  -> PostProcessor.process(rawText)
  -> Metrics.score(reference, raw, processed)
  -> report rows
```

## Configuration

v0.1 uses file-based configuration:

- ASR model paths.
- whisper.cpp binary path.
- benchmark sample manifest path.
- hotword and replacement rules.
- hotkey default documented as `Option + Space`.

Example hotword config:

```json
{
  "protected_terms": ["Codex", "MCP", "SeaTalk", "prelive", "Go", "PR", "issue"],
  "replacements": {
    "皮阿尔": "PR",
    "马克皮": "MCP",
    "扣德克斯": "Codex"
  }
}
```

## Error Handling

Expected error cases:

- Missing microphone permission.
- Missing accessibility permission for paste automation.
- Missing or invalid ASR model path.
- Missing whisper.cpp binary.
- Hotkey registration conflict.
- Empty recording.
- ASR process timeout or non-zero exit.
- Paste failure in the active application.

The app surfaces concise status messages and documents permission steps. The CLI returns non-zero exit codes for setup or benchmark failures.

## Privacy

SwitchType v0.1 must not send audio or transcripts to cloud ASR. Temporary audio files should be written locally, used for transcription, and removed after successful processing unless debug mode is enabled.

## Testing Strategy

Benchmark tests:

- Unit tests for hotword loading.
- Unit tests for post-processing replacements and protected terms.
- Unit tests for metrics calculations.
- Smoke test with example manifest and fake ASR output.

App tests:

- Unit tests for post-processing.
- Unit tests for app state transitions where practical.
- Manual permission checklist for microphone and accessibility.
- Manual end-to-end test in TextEdit or another local text field.

Documentation verification:

- README includes install/setup steps.
- README explains how to download or place models.
- README includes benchmark command examples.
- README includes known limitations.

## Delivery Plan

1. Initialize repository and write design/spec documentation.
2. Build benchmark data format and scoring utilities.
3. Implement deterministic post-processing and tests.
4. Add local ASR runner interface and a whisper.cpp runner.
5. Add SenseVoice/FunASR benchmark runner if local dependencies are available.
6. Generate benchmark report format with example data.
7. Scaffold macOS menu bar app.
8. Implement recording, hotkey events, transcription invocation, post-processing, clipboard paste, and permission guidance.
9. Write README, setup docs, and demo recording instructions.
10. Verify CLI tests, benchmark smoke test, Swift build, and manual app flow.

## Open Risks

- macOS accessibility permission and paste automation may require manual setup and cannot be fully automated in tests.
- SenseVoice/FunASR may add heavy Python dependencies; keeping it benchmark-only prevents blocking the app.
- Accurate Chinese-English mixed scoring needs a pragmatic metric split rather than a single perfect score.
- Full clipboard preservation may be unreliable across apps; v0.1 may overwrite clipboard and document the limitation.
